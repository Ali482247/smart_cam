## Что видно по архитектуре

### Dashboard

Главный файл: `dashboard/three_cam_controller.py`.

Сейчас запись идет по старому HTTP-пути:

1. Dashboard собирает задачу через `build_current_task()`.
2. Перед стартом проверяет все настроенные телефоны через `/status`.
3. Пишет `START_PENDING`.
4. Отправляет `/start?...` на все телефоны через `send_start_fast()`.
5. Если все ответили нормально, пишет `START` и `START_ACK`.
6. При стопе отправляет `/stop`, затем подтверждает сохранение через `confirm_stop_saves()`.
7. Пишет `STOP`, `STOP_SAVE`, `SESSION_CHECK`, `LOG_SAVED`.

Плюсы:

- есть блокировка записи при неполном наборе телефонов;
- есть подтверждение ненулевого файла после stop;
- есть post-stop polling через `/status` и `/videos`;
- есть `BAD`, `SUPERSEDED`, `RETAKE`;
- есть watchdog, который может предупреждать о потере телефона во время записи.

Минусы перед фразами:

- сущность называется `word`, фраза будет засовываться в то же поле;
- нет `phrase_id`, `phrase_text`, `phrase_kind`, `segment_index`, `segment_count`;
- имя файла строится из `wordDir`, значит длинная фраза может сделать длинное/грязное имя файла;
- `SESSION_CHECK` проверяет факт сохранения, но не проверяет ожидаемую длительность, FPS, рассинхрон, audio/video метрики;
- watchdog сейчас по конфигу предупреждает, но не останавливает запись, что нормально для старта фраз, но надо явно показывать в отчете после дубля.

### Mobile

Главный файл: `mobile/three_cam_mobile/lib/main.dart`.

Телефон принимает `/start`, сохраняет параметры в `_session...`, запускает `camera.startVideoRecording()`, при `/stop` делает `camera.stopVideoRecording()`, копирует видео в `ThreeCamVideos/<signer>/<wordDir>/...mp4` и пишет JSON sidecar.

Плюсы:

- metadata JSON уже богатый: `session_id`, `signer`, `word`, `take`, `duration_ms`, `size_bytes`, `mode`, `wordDir`, `gestureCount`, `deviceId`, `recordIndex`;
- есть проверка нулевого файла;
- есть зеркалирование в DCIM;
- есть безопасная очистка имени через `_cleanName`.

Минусы перед фразами:

- `_cleanName` не ограничивает длину, только чистит символы;
- `_recordingFileName()` кладет текстовую базу в имя файла;
- нет лимита длительности, предупреждения о слишком длинной записи, мягкой отсечки или автосегментации;
- `duration_ms` появляется только после стопа, во время записи Dashboard не знает реальную длительность каждого устройства;
- WS adapter сейчас не передает все metadata поля, только часть.

### WS/protobuf слой

В проекте уже есть новый слой: `server/gateway`, `server/scheduler`, `server/network`, `server/connection`, `server/synchronization`, `protocol/*.proto`, мобильный `ws_client.dart`.

Сейчас `ScheduledCommand` содержит:

- `type`;
- `execute_at_ms`;
- `command_id`;
- `camera_name`;
- `session_label`;
- `record_index`.

Для фраз этого мало. Если запускать через WS scheduler, надо расширять протокол metadata-полями или отдельным `RecordingTask`, иначе синхронный старт будет без нормального контекста фразы/дубля.

## Проблема кодировки

В логе и части исходников русские имена выглядят как mojibake, например `РђР·РёР·Р°` вместо нормального имени. Это не ломает запись, но ломает читаемость логов, папок, PDF source names и отчетов.

Рекомендация: перед активной неделей с фразами отдельно починить кодировку источников и состояния:

- хранить все `.py`, `.json`, `.ndjson`, `.md` строго в UTF-8;
- проверить, где были внесены строки `SIGNERS`;
- не делать автоматическую массовую конвертацию без бэкапа, потому что часть данных уже может быть сохранена в поврежденном виде;
- добавить маленький health-check, который ругается, если в signer/source text встречается типичный паттерн `Рђ`, `Рё`, `СЏ`, `вЂ`.

## Рекомендации перед записью фраз

### 1. Ввести отдельную сущность `phrase`

Не стоит просто записывать длинную фразу в `word`. Лучше добавить совместимую модель:

- `mode`: `word | phrase | background`;
- `item_id`: общий ID элемента;
- `word_id`: оставить для старых слов;
- `phrase_id`: новый ID фразы;
- `display_text`: что показываем оператору;
- `file_slug`: короткий стабильный slug для файла;
- `full_text`: полный текст фразы в metadata, не обязательно в имени файла;
- `take_label`;
- `take_number`;
- `retake`;
- `segment_index`;
- `segment_count`.

Так старые слова не сломаются, а фразы получат нормальную структуру.

### 2. Не класть длинный текст фразы в имя файла

Для фраз имя файла лучше делать так:

`phrase_0123_a_device_1_20260907_153000_389.mp4`

А полный текст хранить в `.json` sidecar:

```json
{
  "mode": "phrase",
  "phrase_id": 123,
  "phrase_text": "полный текст длинной фразы...",
  "file_slug": "phrase_0123",
  "take": "a",
  "session_id": "20260907_153000_389"
}
```

Это решает Windows/Android path length, грязные символы, кавычки, скобки, апострофы и очень длинные фразы.

### 3. Добавить проверку длительности после стопа

Сейчас `SESSION_CHECK` говорит только `saved_ok=3`. Для фраз лучше добавить:

- `duration_ms` по каждому телефону;
- `duration_delta_ms` между самым коротким и самым длинным видео;
- `expected_min_duration_ms` и `expected_max_duration_ms`, если заданы;
- warning, если один ракурс сильно короче других;
- warning, если файл слишком маленький для длительности.

Пример правила для начала:

- если `max(duration) - min(duration) > 1500 ms`, пометить `SESSION_WARNING`;
- если `duration < expected_min - 1000 ms`, пометить `SESSION_WARNING`;
- если `size_bytes == 0`, как сейчас, это `SESSION_ERROR`.

### 4. Для длинных фраз дать оператору таймер и мягкие пороги

Нужны не только логи, но и UX:

- elapsed timer крупно во время записи;
- желтая зона после ожидаемой длительности;
- красная зона после hard limit;
- после стопа короткая строка: `Saved 3/3, duration spread 320ms`;
- кнопка `Retake phrase`;
- для длинных фраз кнопка `Mark segment bad`, если будете сегментировать.

### 5. Решить стратегию длинной фразы

Есть три варианта:

1. Цельный дубль. Самый простой. Подходит для фраз до 20-40 секунд.
2. Цельный дубль плюс таймкоды. Лучше для 40-120 секунд: один файл, но внутри metadata есть `segments`.
3. Несколько сегментов. Лучше для очень длинных фраз, но оператору сложнее, а модель данных должна уметь `segment 1/3`.

Мой совет для этой недели: начать с варианта 1 + подготовить metadata под вариант 2. То есть снимать фразу одним дублем, но уже хранить поля, которые потом позволят добавить сегменты без переименования всей системы.

### 6. Не включать авто-стоп watchdog сразу

Текущий конфиг:

- `recording_watchdog_enabled=true`;
- `abort_recording_on_phone_loss=false`;
- `recording_watchdog_can_stop_recording=false`.

Для первых фраз это хорошо. Если телефон моргнул сетью, лучше продолжить запись и показать warning, чем автоматически остановить редкий длинный дубль. После съемки можно решить по `SESSION_WARNING`, переснимать или оставить.

### 7. Протокол WS расширять до перехода на синхронный старт фраз

Если будете использовать WS scheduler для точного старта, надо не только `session_label` передавать. Нужен payload примерно:

```proto
message RecordingTask {
  string mode = 1;
  string signer_id = 2;
  string signer_name = 3;
  string item_id = 4;
  string word_id = 5;
  string phrase_id = 6;
  string display_text = 7;
  string file_slug = 8;
  string take_label = 9;
  uint32 take_number = 10;
  uint32 gesture_count = 11;
  bool retake = 12;
}
```

И добавить его в `ScheduledCommand`. Тогда HTTP и WS пути не будут расходиться по metadata.

## Что я бы сделал первым

1. Добавить `mode=phrase` без удаления `mode=word`.
2. Для фраз генерировать короткий `file_slug`, а полный текст хранить только в metadata.
3. Расширить `SESSION_CHECK` длительностями и warning-ами.
4. Починить/зафиксировать UTF-8 для signer names и логов.
5. Добавить импорт фраз из CSV/JSON/Markdown-таблицы с колонками `phrase_id`, `phrase_text`, `count`, `expected_duration_sec`.
6. Провести тестовую сессию: 10s, 30s, 60s, 120s на 3 телефонах, потом сравнить `duration_ms`, размеры и наличие файлов.

## Итог

По этому логу система записи как `3-camera capture` выглядит стабильной: ошибок сохранения нет, блокировка отсутствующего телефона сработала правильно, задержки ответов маленькие. Для фраз главный шаг - не начинать с хака "длинная фраза как word name", а аккуратно добавить phrase metadata и короткие file names. Это даст меньше боли с файлами, пересъемками и будущей синхронизацией.
