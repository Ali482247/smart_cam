# Clock Synchronization

See [protocol_specification.md](protocol_specification.md) for the `ClockSyncRequest` /
`ClockSyncReply` wire shapes referenced below, and [scheduler.md](scheduler.md) for how
the offset/uncertainty this layer produces gets consumed.

## Why round-trip exchange, not a raw one-way timestamp

Today there is no clock synchronization at all — start/stop happens the instant each
phone's HTTP handler runs, so cross-device skew is whatever the network/OS scheduling
happened to produce that moment. A single one-way timestamp (phone just trusts a
timestamp the server sends) can't separate "the clocks are offset" from "the message
took time to arrive" — both look the same in one direction. A round-trip exchange with
two clocks reporting their own local timestamps at each hop lets you solve for offset
and transit delay separately.

## Exchange algorithm (NTP-style, 4 timestamps)

1. Node sends `ClockSyncRequest{t0 = node's local send time}`.
2. Server receives at `t1` (server clock).
3. Server replies `ClockSyncReply{t0 (echoed), t1, t2 = server's local send time}`.
4. Node receives at `t3` (node's local receive time).

```
roundTripDelay = (t3 - t0) - (t2 - t1)
offset         = ((t1 - t0) + (t2 - t3)) / 2      // server_time - node_time
```

`offset` is what the node adds to a server timestamp to get the equivalent node-local
time; `roundTripDelay` is used to bound confidence in that offset (see below).

## Sampling strategy

- On connect (after `Welcome`), the node runs a **burst of 8 samples**, spaced ~200ms
  apart (avoids the node/server congesting their own exchange).
- Discard outliers: any sample whose `roundTripDelay` exceeds 1.5× the median RTT of the
  batch is dropped (a delayed round trip means the offset estimate for that sample is
  less trustworthy, not that the clock actually jumped).
- Average the `offset` of the remaining samples for the initial estimate.
- **Re-sample every 30-60 seconds** for the rest of the session — phone clocks (often not
  NTP-synced themselves) can drift measurably over a long recording session.

## Confidence tracking

Track a rolling `offsetUncertaintyMs` = half the spread between the max and min offset
in the currently-retained sample set. This number is not cosmetic — it feeds directly
into the Scheduler's lead-time formula (`scheduler.md`): the less confident the offset
estimate, the more lead time is budgeted before `executeAt`, because an uncertain offset
means the node might fire early or late relative to the intended instant.

## Applying the offset

Given a server-clock timestamp `execute_at_ms` (arriving inside a `ScheduledCommand`,
see `protocol_specification.md`) and the node's current `offset` (server − node):

```
localExecuteAtMs = execute_at_ms - offset
```

The node schedules a local timer (`Future.delayed` in Dart, or an await-until-time loop)
for `localExecuteAtMs` and only then calls `_startRecording`/`_stopRecording`.

## On reconnect

Offset and uncertainty state are **invalidated and re-measured from scratch** on every
reconnect (see [connection_lifecycle.md](connection_lifecycle.md) §Session Recovery) —
a gap in the connection is exactly the kind of event that can correlate with clock drift
(e.g. the phone slept, NTP resynced in the background), so a stale pre-disconnect offset
must never be reused as if the gap didn't happen.

## Accuracy target validation plan

Target: **<10ms** cross-node skew on local Wi-Fi. To actually measure this in testing
(not just assert it):

1. Point all CameraNodes at a shared, precisely-timed visible/audible event — e.g. a
   millisecond on-screen counter on a laptop, or a synchronized flash/audio click
   generated by a separate device.
2. Trigger a synchronized `ScheduledCommand` start across all nodes.
3. Compare, frame-by-frame, the captured timestamp of the shared event across each
   node's footage. The spread across nodes is the actual measured skew — compare against
   the <10ms target.
4. Repeat at increasing device counts (4 → 20 → 50, as devices become available) to see
   how skew scales with fan-out size, per the scaling notes in
   [network_architecture.md](network_architecture.md).

## Known limitations

Wi-Fi jitter (microwave interference, AP congestion, other traffic on the same AP) can
transiently blow the RTT budget for a given exchange. This is an accepted risk, not
something this design eliminates — the Scheduler's safety margin (see `scheduler.md`)
is the mitigation, sized to absorb typical jitter, not a guarantee against pathological
network conditions.
