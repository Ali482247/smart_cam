# План реализации Three Cam Dataset Controller

## Цель

Сделать контроллер для быстрой и стабильной записи датасета жестов с нескольких телефонов:

- оператор выбирает signer один раз, выбор сохраняется;
- импортирует PDF/список слов;
- видит текущее слово по центру контроллера;
- нажимает `START REC` и `STOP REC`;
- видео автоматически сохраняются на каждом телефоне в правильную структуру папок;
- можно снимать несколько дублей одного слова;
- можно отмечать плохие видео как `error` и перезаписывать;
- можно отдельно снимать background;
- нельзя начать запись, если не все нужные телефоны подключены;
- можно сбросить индексы или удалить все видео;
- можно временно вернуться назад к старому слову и потом сбросом вернуться к основной позиции.

Главный принцип: не добавлять тяжелых операций в момент `START REC`. Все вычисления имени, папки и текущего задания должны быть готовы на контроллере до старта. Телефон во время записи только пишет видео, а после `STOP REC` быстро копирует файл в уже понятную директорию.

## Что уже есть в проекте

- Python/Tk контроллер: `dashboard/three_cam_controller.py`.
- Flutter-приложение телефона: `mobile/three_cam_mobile/lib/main.dart`.
- HTTP API телефона уже есть:
  - `/start`
  - `/stop`
  - `/status`
  - `/videos`
  - `/clear-videos`
  - `/download`
- Видео сейчас сохраняются на телефоне в `ThreeCamVideos` плоским списком файлов.
- Имя файла сейчас строится примерно так:
  - `<camera_name>_<YYYYMMDD>_<HHMMSS>_<index>.mp4`
- Контроллер уже хранит конфиг в `dashboard/three_cam_controller_config.json`.
- На телефоне уже есть локальные настройки через `shared_preferences`.
- Сохранение после `STOP` сейчас идет асинхронно: телефон отвечает на `/stop`, а копирование файла может еще завершаться после ответа.
- Логи сейчас могут показывать `ERROR`, если ответ от телефона пришел поздно/сломался, даже когда видео фактически сохранилось.

## Основное решение

Добавить понятие `recording_task` - задание записи, которое контроллер отправляет телефонам при старте:

```json
{
  "signer_id": "signer_1",
  "signer_name": "Шоира",
  "mode": "word",
  "word": "apple",
  "take_number": 1,
  "take_label": "a",
  "gesture_count": 2,
  "session_id": "20260806_153012_748",
  "record_index": 748,
  "date": "2026 08 06",
  "time": "153012"
}
```

Для background:

```json
{
  "signer_id": "signer_1",
  "signer_name": "Шоира",
  "mode": "background",
  "word": "background",
  "take_number": 1,
  "take_label": "a"
}
```

Телефон сохраняет видео по этим полям. Контроллер хранит прогресс и управляет переходом слов.

## Формат имени файла

Предлагаемый формат:

```text
<word>_<take_label>_<device_label>_<YYYYMMDD>_<HHMMSS>_<record_index>.mp4
```

Примеры:

```text
apple_a_device_1_20260806_153012_748.mp4
apple_b_device_2_20260806_153155_749.mp4
background_a_device_3_20260806_154000_760.mp4
ERROR_apple_a_device_1_20260806_153012_748.mp4
```

Почему так:

- слово видно сразу;
- дубль виден как `a`, `b`, `c`;
- видно устройство;
- дата/время остаются;
- индекс остается для совместимости с текущей логикой;
- сортировка по имени и по времени остается понятной.

## Импорт PDF и список слов

### Что показали реальные PDF

Изучены два файла из корня проекта:

- `set_01_words_0001_0100.xlsm - Google Sheets.pdf`
- `set_02_words_0101_0200.xlsm - Google Sheets.pdf`

Оба файла:

- экспортированы из Google Sheets через Skia/PDF;
- являются текстовыми PDF, не сканами;
- содержат сжатые `/FlateDecode` text streams;
- используют ToUnicode/CMap шрифты, поэтому простой raw-text может дать мусор вроде `<0016>` или неправильно склеенные буквы;
- визуально имеют табличную структуру:
  - `№`
  - `page`
  - `uzbek`
  - `signer_1`
  - `signer_2`
  - ...
  - `signer_10`
- реальные слова находятся в колонке `uzbek`;
- колонки `signer_1 ... signer_10` в этих PDF являются таблицей контроля/разметки, а не списком людей для выбора в приложении;
- в конце есть строка `ФОН`, ее нужно трактовать как подсказку для background mode, а не как обычное слово очереди;
- внутри страниц встречаются служебные строки/footers из печати Google Sheets, например дата/страница, их нужно фильтровать;
- часть слов визуально может разбиваться PDF-координатами на фрагменты, например `M | ening`, `Sevm | oq`, `Esh | ik`; импорт должен склеивать фрагменты одной ячейки `uzbek`.

Первые реальные строки `set_01`:

```text
1  | page 12 | Tashakkur, minnatdorchilik
2  | page 12 | Sizning (sening, uning, ularning)
3  | page 12 | Birdan, to'satdan (vo-qea, tasodif)
4  | page 13 | To'g'ri (haq, rost)
5  | page 13 | Birgalikda (birga)
...
100 | page 48 | Aziz (qimmatli, qimmat)
```

Первые реальные строки `set_02`:

```text
101 | page 48 | Qiz
102 | page 48 | Amaki, tog'a
103 | page 49 | Xotin, rafiqa
104 | page 49 | Ayol
105 | page 49 | Hayot (yashamoq)
...
200 | page 83 | Mebel
```

Вывод для реализации: импорт должен быть table-aware. Нельзя просто брать каждую строку PDF как слово, потому что там есть заголовки, номера страниц, signer-колонки, footer и иногда разрезанные слова.

### Что нужно реализовать

В контроллер добавить кнопку `IMPORT PDF`.

После выбора PDF:

1. Контроллер извлекает табличные строки из PDF.
2. Берет только колонку `uzbek`.
3. Сохраняет вместе со словом служебные поля:
   - `word_id` из колонки `№`;
   - `page` из колонки `page`;
   - `uzbek` из колонки `uzbek`;
   - `source_pdf`;
   - `source_set`, например `set_01` или `set_02`.
4. Нормализует слова:
   - trim пробелов;
   - убрать пустые строки;
   - сохранить порядок;
   - не ломать кириллицу/латиницу;
   - склеить PDF-фрагменты внутри одной ячейки, например `M | ening` -> `Mening`;
   - убрать переносы с дефисом только там, где они явно появились от переноса строки, например `ber-moq` можно оставить как в PDF, а `vo-qea` не исправлять автоматически без словаря;
   - одинаковые слова можно оставить, но показать warning с номерами.
5. Игнорирует служебные строки:
   - `page | uzbek | signer_...`;
   - `I = №`, `II = №`;
   - footer/date/page-number;
   - пустые строки;
   - `ФОН` как обычное слово.
6. Если найдена строка `ФОН`, контроллер может показать info: `PDF содержит ФОН, используйте BACKGROUND mode для съемки фона`.
7. Показывает текущее слово большим текстом по центру.
8. Сохраняет импортированный список в файл состояния, чтобы после перезапуска контроллер не потерял очередь.

### Как извлекать эти PDF надежно

Основной вариант:

- использовать `pypdf` для чтения страниц;
- если `extract_text()` вернул нормальную таблицу, распарсить строки регуляркой:

```text
<word_id> <page> <uzbek text>
```

Fallback для Google Sheets PDF:

- читать PDF content streams;
- распаковывать `/FlateDecode`;
- использовать `/ToUnicode` CMap для декодирования glyph ids;
- собирать текстовые элементы по координатам `x/y`;
- группировать элементы в строки по `y`;
- определять колонки по `x`:
  - колонка 1: `word_id`;
  - колонка 2: `page`;
  - колонка 3: `uzbek`;
  - остальные signer-колонки игнорировать;
- склеивать фрагменты внутри одной `uzbek` ячейки.

Это нужно потому, что реальные файлы Google Sheets могут декодироваться не как простые строки. При неправильном чтении появляются разрезы вроде `M | ening`, `Er | kak`, `Esh | ik`.

### Поведение при нескольких PDF

Импорт должен поддерживать выбор одного или нескольких PDF сразу.

Если выбраны:

```text
set_01_words_0001_0100.xlsm - Google Sheets.pdf
set_02_words_0101_0200.xlsm - Google Sheets.pdf
```

контроллер должен собрать единую очередь:

```text
1..100 из set_01
101..200 из set_02
```

Сортировка:

- сначала по `word_id`, если все номера распознаны;
- если номера отсутствуют, по порядку страниц/строк внутри выбранных PDF;
- при дубле `word_id` показать warning и оставить порядок импорта.

### Зависимость для PDF

В Python лучше использовать `pypdf`, потому что это маленькая библиотека и ее достаточно для текстового PDF.

Fallback, если PDF окажется сканом:

- показать понятный warning: `PDF не содержит текст. Нужен текстовый PDF или OCR.`
- не пытаться делать OCR в первом этапе, чтобы не добавлять тяжелую зависимость и задержки.

## Количество жестов на слово

В UI добавить поле `Gestures per word`, default `1`.

Логика:

- если значение `1`, после каждого успешного `STOP REC` перейти к следующему слову;
- если значение `2`, одно и то же слово записывается два раза:
  - первый дубль: `word_a`;
  - второй дубль: `word_b`;
  - только после второго `STOP REC` перейти к следующему слову;
- если значение `3`, будут `word_a`, `word_b`, `word_c`;
- если больше 26, после `z` использовать `aa`, `ab`, но на практике лучше ограничить UI до разумного диапазона, например `1..10`.

Слово меняется только после успешного завершения stop workflow, а не сразу после start.

## Workflow обычной записи

1. Оператор выбирает signer.
2. Оператор импортирует PDF.
3. Контроллер показывает первое слово.
4. Оператор нажимает `START REC`.
5. Контроллер проверяет:
   - signer выбран;
   - есть текущий word;
   - все нужные телефоны online;
   - телефоны не уже в записи;
   - свободная память и батарея ок, если включена проверка.
6. Контроллер заранее создает `recording_task`.
7. Контроллер отправляет `/start` на все телефоны с query-полями задания.
8. Телефоны начинают запись без создания тяжелых структур в UI-потоке.
9. Оператор нажимает `STOP REC`.
10. Контроллер отправляет `/stop`.
11. Телефон останавливает камеру и сохраняет файл в:
    - `ThreeCamVideos/<signer>/<word>/...mp4`
    - при включенном `saveToGallery` также в `DCIM/ThreeCam/<signer>/<word>/...mp4`, если Android MediaStore позволит относительные папки.
12. Контроллер обновляет список видео.
13. Если все ожидаемые телефоны вернули сохраненное видео, прогресс дубля засчитывается.
14. Если дублей для слова достаточно, контроллер переходит к следующему слову.
15. Если часть телефонов не подтвердила сохранение, контроллер показывает warning и не двигает слово автоматически, пока оператор не решит.

## Исправление логов

Текущая проблема: контроллер пишет `ERROR`, хотя видео может быть сохранено.

Новая логика:

- сетевые ошибки на `/stop` не считать сразу ошибкой сохранения;
- после `/stop` делать короткую проверку `/status` и `/videos`;
- если новое видео появилось, писать `SAVED`;
- если команда stop отправлена, но подтверждение сохранения задержалось, писать `WAITING SAVE`;
- если после нескольких коротких проверок видео не появилось, писать `WARNING`, а не общий `ERROR`;
- настоящий `ERROR` писать только когда:
  - телефон явно вернул `{ok:false}`;
  - камера не готова;
  - файл не создался после таймаута проверки;
  - endpoint недоступен до начала записи.

Пример лога:

```text
START: sent to 3/3 phones, word=apple, take=a
STOP: command accepted by 3/3 phones
SAVE: device_1 saved apple_a_device_1_20260806_153012_748.mp4
SAVE: device_2 saved apple_a_device_2_20260806_153012_748.mp4
SAVE: device_3 saved apple_a_device_3_20260806_153012_748.mp4
NEXT WORD: salom
```

Если один телефон ответил медленно:

```text
STOP: command accepted by 2/3 phones, checking saved videos...
SAVE: device_3 saved after 1.2s
```

Если реально проблема:

```text
WARNING: device_2 did not confirm saved video for apple_a after 5s
```

## Список видео в контроллере

Добавить таблицу `Saved videos`:

Колонки:

- signer;
- word/mode;
- take;
- device;
- filename;
- size;
- modified;
- status: `OK` или `ERROR`.

Источник данных:

- контроллер вызывает `/videos` на телефонах;
- телефон возвращает не только имя файла, но и metadata:
  - `signerId`;
  - `signerName`;
  - `word`;
  - `mode`;
  - `takeLabel`;
  - `recordIndex`;
  - `relativePath`;
  - `isError`.

Чтобы не парсить все только из имени, рядом с видео на телефоне нужно хранить маленький JSON metadata-файл:

```text
apple_a_device_1_20260806_153012_748.mp4
apple_a_device_1_20260806_153012_748.json
```

Пример metadata:

```json
{
  "signer_id": "signer_1",
  "signer_name": "Шоира",
  "word": "apple",
  "mode": "word",
  "take_label": "a",
  "record_index": 748,
  "device_label": "device_1",
  "created_at": "2026-08-06T15:30:12",
  "status": "ok"
}
```

Это даст стабильную работу даже если имя файла поменяется.

## Отметка видео как error

В контроллере:

1. Оператор кликает на видео в таблице.
2. Открывается маленькое окно/панель действий:
   - `Mark error`;
   - `Retake`.
3. Если выбран `Mark error`, появляется кнопка `Save`.
4. После `Save` контроллер вызывает новый endpoint телефона:

```text
POST /mark-video-error?path=<relativePath>
```

Телефон:

- проверяет, что файл находится внутри `ThreeCamVideos`;
- переименовывает файл, добавляя `ERROR_` в начало имени;
- обновляет metadata `status: "error"`;
- возвращает новое имя/путь.

Контроллер обновляет таблицу.

## Перезапись видео

Кнопка `Retake` должна работать так:

1. Контроллер берет metadata выбранного видео:
   - signer;
   - word;
   - mode;
   - take_label;
   - record_index.
2. Устанавливает временное задание retake.
3. Показывает это слово по центру.
4. Следующие `START REC`/`STOP REC` пишут новое видео для этого же слова и дубля.
5. Старое видео не удаляется автоматически.
6. Если старое видео плохое, оператор отдельно помечает его `error`.

Имя нового retake:

```text
apple_a_retake1_device_1_20260806_160000_800.mp4
```

Если клиент хочет именно заменить файл, можно сделать replace-mode, но безопаснее не удалять старый материал.

## Background mode

В UI добавить toggle `BACKGROUND`.

Когда toggle включен:

- текущее слово заменяется на `BACKGROUND`;
- progress слов не двигается;
- `START REC` создает задание `mode=background`;
- `STOP REC` сохраняет видео в:

```text
ThreeCamVideos/<signer>/background/
```

После выключения background:

- контроллер возвращает текущее слово туда, где был до включения;
- счетчик дублей слов не меняется.

Background совместим с:

- выбранным signer;
- списком видео;
- отметкой `error`;
- retake;
- delete videos;
- reset index.

## Reset index

Добавить кнопку `RESET INDEX`.

Что делает:

- сбрасывает `next_index` в контроллере на `0`;
- вызывает новый endpoint на телефонах:

```text
POST /reset-index
```

Телефон:

- сбрасывает `_localIndex = 0`;
- не удаляет видео;
- следующий новый файл получит индекс с учетом выбранной политики.

Важный вопрос для подтверждения клиентом:

- если старые видео остаются, а индекс сброшен в `0`, возможны одинаковые индексы в новых именах;
- из-за даты/времени имя файла все равно не совпадет;
- если нужен строгий пересчет/переименование всех старых файлов, это тяжелее и рискованнее.

Мое предложение: `RESET INDEX` сбрасывает счетчик будущих записей, но не переименовывает старые файлы. Это быстро и безопасно. Если заказчик под `в файлах на телефоне` имеет в виду переименовать все существующие видео, это нужно подтвердить отдельно.

## Проверка подключенных телефонов

Добавить строгую проверку перед `START REC`.

В конфиге уже есть `min_phones`, но нужно сделать понятнее:

```json
{
  "required_phone_count": 3,
  "block_recording_if_missing_phones": true
}
```

Перед стартом:

- контроллер опрашивает `/status` всех сохраненных телефонов;
- если online меньше `required_phone_count`, запись запрещается;
- показывается warning:

```text
WARNING: connected 2/3 phones. Recording blocked.
Missing: device_3 http://192.168.0.102:8088
```

Если все телефоны обычно подключены, эта проверка почти ничего не меняет, но защищает от случайной потери камеры.

Чтобы не было задержек:

- status проверять параллельно через `ThreadPoolExecutor`;
- timeout держать короткий, например `1.0-1.5s`;
- использовать кэш статуса из polling, если он свежий.

## Возврат назад по словам

Нужны две позиции:

- `main_word_index` - где оператор находится в основной очереди;
- `view_word_index` - какое слово сейчас временно показано.

Обычная запись двигает `main_word_index`.

Кнопка назад:

- уменьшает `view_word_index`;
- включает `manual_back_mode`;
- показывает старое слово;
- `START REC`/`STOP REC` в этом режиме записывают выбранное старое слово;
- после stop слово автоматически не прыгает вперед.

Кнопка `RESET VIEW` или `СБРОС`:

- выключает `manual_back_mode`;
- возвращает `view_word_index = main_word_index`;
- показывает слово основной очереди.

Пример:

1. Есть слова: `TASHQARI`, `ALI`, `SALOM`.
2. Записали `TASHQARI`, контроллер перешел на `ALI`.
3. Записали `ALI`, контроллер перешел на `SALOM`.
4. Оператор нажал назад два раза, увидел `TASHQARI`.
5. Записал дополнительный `TASHQARI`.
6. Слово не меняется автоматически, потому что это manual back mode.
7. Оператор нажал `СБРОС`.
8. Контроллер вернулся на `SALOM`.

Так мы не ломаем основной прогресс, но даем спокойно доснять старые слова.

## Совместимость HTTP и WS

Сейчас основные кнопки `START REC`/`STOP REC` используют HTTP, а `SYNC START` использует WS Scheduler.

Для первого этапа все новые dataset-функции лучше привязать к HTTP path, потому что:

- он уже передает query params;
- его проще быстро расширить;
- текущий рабочий workflow оператора уже на `START REC`;
- меньше риск сломать синхронизацию WS.

WS оставить рабочим как есть. После подтверждения HTTP workflow можно расширить `scheduler.proto`, добавив в `ScheduledCommand` поля signer/word/mode/take.

## Без задержек

Чтобы UI работал быстро:

- все сетевые операции выполнять в background thread, как сейчас через `run_background`;
- не читать PDF во время записи;
- не сканировать все видео перед каждым start;
- после stop обновлять только текущую папку/последние видео;
- `/videos` возвращать отсортированный список, но при большом количестве файлов добавить limit;
- metadata читать только маленькие `.json`, не открывать сами `.mp4`;
- status polling использовать как кэш для проверки connected phones;
- файловые операции на телефоне делать после `stopVideoRecording`, не во время записи.
